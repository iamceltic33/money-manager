# Главная → все операции

Статус: все пять шагов реализованы к 2 октября 2026. Пользователь подтвердил работу жеста и восстановление сводки после исправления. Новые кнопки, web wheel, клавиатура и экранный диктор ещё требуют проверки интерфейса.

## Поведение

- На главной — сводка и ограниченный список последних операций. Предлагаемый начальный размер: 20 записей; он уточняется при проверке на устройстве.
- Перетягивание списка вверх раскрывает историю всех операций. Верхняя часть содержимого главной (сводка и переключатель дохода/расхода) постепенно сжимается и исчезает, а на её месте появляется панель «Фильтры». Общая шапка с балансом и синхронизацией остаётся.
- Анимация следует за движением пальца. После отпускания достаточное расстояние или скорость завершают раскрытие, иначе интерфейс возвращается в исходное положение. Начальные пороги подбираются на устройстве.
- В раскрытом состоянии тот же список продолжает обычную прокрутку. Переход не должен пересоздавать строки, сбрасывать позицию или показывать вторую анимацию навигации.
- «Назад» возвращает главную и восстанавливает сводку. Предлагаемый дополнительный жест: потянуть вниз в самом начале истории для обратного перехода; обычная прокрутка вниз внутри истории не закрывает её.
- Нажатие на операцию открывает её детали. Возврат из деталей сохраняет режим, фильтры и положение списка.
- Для web — раскрытие при прокрутке колёсиком/трекпадом; для пользователей экранного диктора и клавиатуры — отдельное доступное действие «Все операции», не зависящее от жеста.
- Кнопка «Все» заменяется на «Отчёты». Отчёты отложены: до их реализации кнопка явно недоступна с пояснением «Скоро», без перехода в историю или пустой рабочий раздел.
- Раскрытие доступно и при пустом списке: пользователь видит пустое состояние, может открыть фильтры.

## Экран и анимация

Предпочтительный подход: общий компонент главной и истории с одним виртуализированным списком и двумя режимами. Существующий адрес `/transactions` сохраняется для прямого входа в раскрытый режим. Роутер остаётся тонким; UI и состояние располагаются в `src/pages`.

Перед реализацией проверить, как смена адреса и системная кнопка Android «Назад» будут работать без размонтирования общего списка. Не строить переход как завершение жеста на главной с последующим обычным `router.push`, который визуально начнёт переход заново. Если сохранение одного списка между адресами требует изменения структуры маршрутов, сначала подготовить конкретную схему маршрутов.

Жесты и анимация — на уже установленных Gesture Handler и Reanimated, совместимых с Expo 57. При reduced motion использовать короткую смену состояний без масштабирования. Нажатия на строки и горизонтальные жесты не должны запускать раскрытие. Модальное окно фильтров блокирует жест перехода.

## Подгрузка операций

- Разделить виртуализацию и чтение данных: список рисует видимые строки, API читает страницы из локальной SQLite. Увеличение `slice` уже загруженного массива не считается полноценной подгрузкой.
- Предлагаемый размер страницы истории: 40 записей. Загружать следующую порцию до достижения конца видимого списка; показывать индикатор внизу при ожидании и повторную попытку при ошибке.
- Использовать курсор по стабильному порядку `occurred_at DESC, created_at DESC, id DESC`. Добавить подходящий индекс с учётом `user_id`; проверить запросы на реальной схеме и объёме данных.
- Фильтровать тип, категории и даты в SQL до применения лимита. Смена фильтров сбрасывает курсор и возвращает список наверх. Поздние ответы старого запроса/аккаунта не попадают в новый список.
- Исключить параллельные запросы одной страницы и дубли по `id`; отмечать конец данных. Новые операции, редактирование, удаление и завершение синхронизации инвалидируют страницы. После возврата из деталей сохранять позицию по ID, насколько это возможно после изменений.
- Детали и редактирование должны уметь получать запись по ID из БД, даже если соответствующая страница ещё не загружена.
- Баланс считается по всем операциям, а не по загруженным страницам. Прогнозы продолжают получать все необходимые данные. Не заменять глобальную `history` частичным массивом без отдельной адаптации потребителей.
- Отдельно проверить, где ещё остаётся полное чтение истории: текущая инициализация и обновление store читают её целиком. Пагинация экрана сама по себе не устраняет эту нагрузку. В рамках переделки разделить данные списка и потребности расчётов; сохранить текущие финансовые правила и приоритет локальных изменений при синхронизации.

## Порядок реализации

1. Подготовить API страниц, устойчивый курсор, индексы и получение деталей по ID; определить отдельные источники данных для баланса и прогнозов.
2. Вынести общую строку операции и заменить полную отрисовку истории виртуализированным списком. Подключить подгрузку, фильтры и обновление после изменений.
3. Объединить главную и историю на уровне общего UI, сохранив прямой вход `/transactions` и поведение «Назад».
4. Добавить управляемое перетягивание, сворачивание верхней части и появление фильтров. Обеспечить отмену жеста и возврат из деталей.
5. Заменить «Все» на отложенную кнопку «Отчёты», добавить доступное действие открытия истории и поведение web.

## Проверка результата

- Пустой аккаунт, меньше страницы, много страниц; одинаковые даты и время создания, отрицательный/нулевой баланс.
- Все существующие фильтры, отсутствие результатов и сброс фильтров во время загрузки.
- Отмена и завершение жеста, обычная прокрутка раскрытого списка, нажатия на строки, системный возврат и прямой вход в историю.
- Создание/изменение/удаление операции и синхронизация во время подгрузки; смена аккаунта; отсутствие дублей и пропусков после обновления страниц.
- Работа без интернета, ошибка локального чтения и повторная попытка; сохранение позиции после деталей.
- Android release APK: плавность жеста, время открытия истории, число отрисованных строк и объём чтения БД. Сравнить с текущей версией на том же устройстве и данных. Дополнительно проверить iOS/web и reduced motion.

Связанный контекст: [отложенная диагностика задержек](performance-issues.md). Отчёты и остальные кандидаты оптимизации из этого документа остаются отдельными задачами.

## Первый шаг — выполнено

`getLocalTransactionsPage({ userId, limit, cursor, filters })` возвращает `items`, `hasMore` и `nextCursor`. По умолчанию — 40 записей, допустимый лимит 1–200. Тип, категории и включительные границы дат применяются в SQLite до лимита. Пустой массив категорий означает отсутствие ограничения. Даты передаются как `Date`, границы календарного дня определяет вызывающий экран.

Курсор содержит `occurredAt`, `createdAt`, `id` последней возвращённой записи. Сортировка — `occurred_at DESC, created_at DESC, id DESC`; для определения конца читается одна дополнительная запись. Курсор используют только с исходным аккаунтом и фильтрами; смена параметров или изменение данных требует сброса страниц на уровне будущего состояния списка. Это не снимок БД: изменения во время просмотра обрабатываются инвалидацией, которая будет подключена во втором шаге.

Миграция v9 добавляет `transactions_user_page_idx` по `user_id` и трём полям сортировки. Индекс проверен через `EXPLAIN QUERY PLAN` в тестовой SQLite: поиск использует индекс, дополнительная сортировка не требуется. Это проверка плана запроса, не замер скорости на Android.

`getLocalTransactionById(userId, id)` уже доступен и читает напрямую из SQLite, независимо от страниц. Проверена изоляция аккаунтов. Переключение экранов деталей/редактирования с синхронного поиска в store на этот API входит в подключение UI.

Источники данных для следующих шагов:

| Потребитель | Источник | Объём |
| --- | --- | --- |
| Главная и история | `getLocalTransactionsPage` | 20 последних / страницы по 40 |
| Баланс | `getLocalBalance` | SQL-сумма по всем операциям аккаунта |
| Детали и редактирование | `getLocalTransactionById` | Одна запись по ID и аккаунту |
| Прогнозы | `getLocalTransactions` + категории + полный баланс | Полная история для существующего расчёта |
| Синхронизация | Существующие запросы синхронизации | Не зависит от страниц UI |

В первом шаге глобальная `history` остаётся полной и существующие экраны работают как раньше. Во втором шаге данные списка выделяются в отдельное состояние с курсором, фильтрами и инвалидацией; полную историю для прогнозов следует загружать отдельно при открытии прогнозов, обновлять после изменений данных и защищать от смены аккаунта. Вслед за адаптацией всех потребителей можно убрать полную загрузку из инициализации и обновлений глобального store. Формулы прогнозов, правила исключений и расчёт баланса не меняются.

Проверка: тесты `tests/transaction-pages.test.cjs` работают с настоящей SQLite в памяти и проверяют страницы, одинаковые даты, границы фильтров, баланс, доступ по ID, удаление курсора и миграцию существующей БД. На устройстве первый шаг не проверялся.


## Второй шаг — выполнено

История использует `FlatList`, общую `TransactionRow` и страницы SQLite по 40 операций. Фильтры остаются одним объектом, SQL получает тип, категории и границы дат. Смена фильтров возвращает прокрутку наверх; пустой результат отличён от загрузки и ошибки. Ошибка следующей страницы сохраняет существующие строки и курсор, дальнейшее чтение возобновляется кнопкой «Повторить».

Отдельное состояние страниц предотвращает параллельные запросы, удаляет дубли по ID и отбрасывает ответы предыдущего запроса после изменения аккаунта, фильтров или ревизии данных. После CRUD и `refresh()` (включая завершение синхронизации) ревизия меняется и страницы перечитываются. Изменение набора категорий также инвалидирует страницы, в том числе после удаления категории и обнуления её связей в SQLite.

Глобальный store хранит только полный баланс, 20 последних операций (`recentTransactions`), готовность и ревизию. Полная история больше не читается при старте, сохранении и обычном обновлении store. Главная использует ограниченный список и общую строку; её жест и объединение со списком истории остаются следующими шагами.

Детали и редактирование читают отдельную операцию по ID из SQLite с обработкой загрузки, ошибки и повторной попытки. Данные предыдущего ID/аккаунта не отображаются. Форма редактирования сохраняет полученный снимок до сохранения: смена ревизии при фоновой синхронизации не размонтирует форму и не сбрасывает ввод.

Прогнозы загружают полную историю только при активном экране, отдельно от страниц. Смена аккаунта и ревизии защищена от устаревших результатов, ошибка доступна для повторной попытки. Формулы прогнозов и SQL-сумма баланса не изменены.

Во втором шаге при возвращении из деталей без изменений оставались загруженные страницы, фильтры и прокрутка. Восстановление после изменения данных добавлено в третьем шаге ниже.

Проверено: TypeScript, ESLint, 37 тестов; Android JS/Hermes export. Тесты проверяют SQLite, состояния запросов, инвалидацию после CRUD/refresh, полный баланс при ограниченном списке, устаревшие ответы, ошибки и сохранение снимка редактирования. Реальная прокрутка, количество смонтированных строк и внешний вид на устройстве не проверены. Web export не завершён: Metro не разрешает `.wasm` из `expo-sqlite` при текущей конфигурации проекта.

После второго шага пользователь обнаружил регрессию строки: иконка и сумма располагались вертикально, название/дата не были видны. В установленном Expo Router `Link asChild` объединяет стили через Slot; стиль-функция дочернего `Pressable` не сохраняет разметку строки. Исправлено переносом разметки и реакции на нажатие во внутренний `View`, а внешнему `Pressable` задан статический стиль. TypeScript и ESLint прошли; визуальное подтверждение исправления на устройстве ещё отсутствует.

## Третий шаг — выполнено

Главная и история используют `HomeHistoryPage` в `src/pages/home-history` с одним постоянным `FlatList`. Общий экран расположен рядом со стеком маршрутов в layout приложения: переход между `/` и `/transactions` переключает режим без размонтирования списка и без дополнительной анимации навигации. При открытии деталей или формы общий экран скрывается, сохраняя состояние. Маршруты остаются тонкими адаптерами; прямой вход `/transactions` открывает историю.

На главной показаны сводка, переключатель дохода/расхода и 20 последних операций; в истории — фильтры и страницы по 40. Кнопка «Все» пока переключает режим; её замена и жест относятся к следующим шагам. Полная история не запрашивается до открытия истории.

Кнопка в общей шапке и системная кнопка Android возвращают из истории на главную. Из деталей возврат ведёт в исходный режим; при прямом входе в детали без предыдущего маршрута — в историю. Фильтры и позиции главной/истории хранятся отдельно в общем экране.

После инвалидации данных перечитывается ранее загруженный диапазон, затем предпринимается восстановление по ID видимой операции. При смене фильтров диапазон и позиция сбрасываются. Если якорная операция удалена, используется прежнее смещение; для ещё не измеренной строки — оценка смещения по средней высоте. Точность восстановления при изменении данных и размеров строк требует проверки на устройстве.

Проверено: TypeScript, ESLint, 38 тестов и Android JS/Hermes export. Новый тест проверяет перечитывание нескольких ранее посещённых страниц после инвалидации и сброс диапазона при смене фильтров. Навигация, внешний вид и прокрутка на устройстве не проверены. Ограничение web export из второго шага остаётся.


## Четвёртый шаг — реализовано

Перетягивание вверх на списке главной управляет сжатием и небольшим уменьшением сводки, исчезновением заголовка последних операций и проявлением панели фильтров. После отпускания переход завершается при прохождении 45% дистанции или быстром движении (не менее 24 точек и 800 точек/с). Дистанция зависит от измеренной высоты сводки и ограничена 120–240 точками. Незавершённый и отменённый жест возвращают исходное состояние.

Маршрут меняется после завершения анимации. На главной обычная прокрутка списка выключена: движение вверх раскрывает историю. В истории список прокручивается как обычно; обратный жест вниз доступен только если касание началось вверху. Горизонтальные движения и нажатия не активируют переход; фильтры и неактивный экран отключают жест. Анимация отменяется при смене режима или активности экрана. При reduced motion нет интерактивного масштабирования и завершение происходит без анимации.

Обработчик жеста использует ручную активацию Gesture Handler; нативный скролл ждёт определения направления, затем получает движение при отказе обработчика перехода. В корневом layout добавлен `GestureHandlerRootView`. Сворачивание сводки и прозрачность панелей работают через Reanimated, один `FlatList` остаётся смонтированным.

Проверки: TypeScript, ESLint, Android JS/Hermes export и 41 тест. Три новых теста с заменёнными адаптерами Gesture Handler/Reanimated проверяют условия открытия/отмены, обратный жест только в начале, горизонтальное движение, отложенную навигацию, прерванное завершение, отключение и reduced motion. Они не проверяют нативное распознавание касаний, плавность, взаимодействие с нажатием строки и реальную прокрутку. Эти проверки и подбор порогов остаются для устройства. Web wheel и замена «Все» ещё не реализованы.

После пользовательской проверки исправлено восстановление сводки: измеряемое содержимое вынесено в абсолютно расположенный внутренний блок, высота которого не зависит от сжимающейся обёртки. Нулевая высота layout не перезаписывает последнее положительное измерение. Добавлен тест полного восстановления высоты, прозрачности и масштаба при закрытии истории. TypeScript, ESLint и четыре теста перехода прошли; восстановление на устройстве ещё не подтверждено.


## Пятый шаг — реализовано

В заголовке последних операций вместо «Все» показана отключённая кнопка «Отчёты» с подписью «Скоро» и accessibilityState disabled. Перехода и логики отчётов нет. Под заголовком размещено отдельное доступное действие «Все операции»: обычный Pressable открывает историю, доступен для клавиатуры и экранного диктора и работает при пустом списке.

На web прокрутка вниз над списком главной открывает историю после накопления 80 пикселей в серии событий с паузами до 200 мс. Единицы строк и страниц нормализуются; горизонтальное движение, Ctrl+wheel (масштабирование браузера) и движение вверх не открывают историю. Серия открывает историю один раз.
