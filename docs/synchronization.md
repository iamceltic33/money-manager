# Двусторонняя синхронизация

Точка входа — `synchronize(userId)` из `features/sync`. Сейчас запускается при
входе в аккаунт/открытии авторизованной части приложения и кнопкой справа от
баланса. Во время обмена кнопка показывает индикатор загрузки и блокирует повторное
нажатие, в том числе при автоматическом запуске. После ручного обмена обновляются
категории и операции, результат показывается уведомлением. Расписание и фоновый
запуск пока не добавлены. Одновременные вызовы для одного
аккаунта используют один Promise; разные аккаунты обрабатываются последовательно.

Интерфейс сначала читает SQLite, затем обновляет данные после обмена. Ошибка сети
не блокирует работу с уже сохранёнными данными. На новом устройстве стандартные
категории появятся после первого успешного подключения к облаку.

## Порядок обмена

1. `initialize_account_data` под блокировкой профиля однократно создаёт стандартные
   категории для нового пустого аккаунта. При наличии локальных данных или маркера
   `local_users` создание стандартных категорий не запрашивается. Серверный
   `profiles.data_initialized_at` не позволяет повторно создать их на другом
   устройстве или после удаления всех категорий.
2. Отправляется очередь удалений: операции, затем категории. Удаление отсутствующей
   облачной записи считается успешным. Очередь очищается только после ответа сервера.
3. Отправляются категории, затем операции. Операция с ещё не отправленной категорией
   остаётся `pending`. Для записи используется стабильный UUID.
4. Повторно отправляются удаления, возникшие во время запросов. До трёх проходов
   позволяют отправить свежие локальные правки без бесконечного цикла. Оставшиеся
   `pending` сохраняются для следующего запуска.
5. `get_sync_snapshot` возвращает обе таблицы одним согласованным SQL-снимком.
   В отличие от постраничных запросов, он не теряет строки из-за изменений между
   страницами и не обрезает результат стандартным лимитом REST в 1000 строк.
6. SQLite принимает изменения и удаления из снимка только для `synced`-записей.
   Категории загружаются перед операциями. Локальные `pending`, `failed` и очередь
   удалений защищены от перезаписи. Удаления, пришедшие из облака, не создают
   повторное задание на отправку.

## Защита изменений

SQLite v8 добавляет `local_revision`, `remote_updated_at`, `remote_deleted` и версию
задания удаления. Триггер увеличивает локальную версию при изменении бизнес-полей,
включая две правки с одинаковым временем. Подтверждение отправки сверяет именно эту
версию: старая отправка не помечает более новую правку как `synced`.

При конфликте приоритет имеет локальная запись со статусом `pending` или `failed`.
`apply_sync_change` записывает её содержимое независимо от времени облачной версии.
Совпадение содержимого делает повтор после потери ответа безопасным. Если запись
удалена в облаке, локальная правка восстанавливает её с прежним UUID. Перед отправкой
операции восстанавливается отсутствующая связанная категория; существующая категория
без локальных правок при этом не перезаписывается.

Для записей без локальных изменений принимаются облачные правки и удаления.
Локальное явное удаление имеет приоритет над облачной правкой. При последовательной
отправке правок с двух устройств побеждает последняя отправленная локальная версия;
время редактирования не используется для выбора победителя. `expected_updated_at`
остаётся в сигнатуре RPC для совместимости, но больше не блокирует отправку.

Каждый запуск использует отдельный клиент с зафиксированным токеном текущего
аккаунта. Серверные RPC работают как `security invoker`, с RLS; служебный ключ
не используется. Ответ старого аккаунта не возвращается в Zustand после выхода.

## Границы текущего решения

- Полный снимок подходит текущему объёму данных. Для большой истории потребуется
  журнал изменений и курсор, включая серверные отметки удаления.
- Старые дубли категорий и несовпадающие локальный/облачный ID требуют явного
  исправления; автоматическое объединение данных не выполняется.
- Ошибки доступа, сети и ограничения уникальности по-прежнему сохраняют запись для повтора; приоритет локальных правок не обходит RLS и ограничения базы.
- Удаления до появления локальной очереди восстановить невозможно.

Проверка локальных сценариев: `npm run test:sync` (Node.js с `node:sqlite`).

## Результат проверки 23 сентября 2026

Прошли TypeScript, ESLint и 14 локальных тестов. В реальном Supabase с двумя
временными аккаунтами и тремя независимыми SQLite-базами подтверждены:

- Одновременная первичная инициализация создаёт ровно семь категорий; второе устройство получает те же ID.
- Изменения передаются в обе стороны; редактирование во время отправки сохраняется.
- Повтор после потери ответа на уже выполненную запись не создаёт дублей.
- На момент первоначальной проверки конфликт возвращал ошибку. Позже правило изменено на приоритет локальных правок.
- Удаление доходит до второго устройства без повторного задания в очереди.
- Новые RPC соблюдают изоляцию аккаунтов и запрещают чужую категорию.
- Снимок загружает все 1005 тестовых операций.
- После удаления всех категорий на третьем устройстве они не создаются заново.

Четыре временных аккаунта текущего и прерванного запусков удалены. Контрольный
запрос подтвердил отсутствие их профилей, категорий и операций.

Интерфейс на физическом устройстве или эмуляторе в эту проверку не входил.

После изменения правила на приоритет локальных правок прошли 17 локальных тестов,
TypeScript и ESLint. На временном аккаунте Supabase дополнительно проверены:
перезапись конфликтующих категорий и операций локальными правками, приём облачных
правок без локальных изменений, восстановление удалённой операции со связанной
категорией без дублей, редактирование во время отправки и отправка локального удаления.
Миграция `20260923000000_local_changes_take_priority.sql` применена в облаке.
