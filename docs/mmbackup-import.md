# Импорт Money Manager (.mmbackup)

`scripts/prepare-mmbackup-import.py` читает резервную копию Android-приложения и готовит SQL для **замены** категорий и операций одного аккаунта. Скрипт сам не подключается к Supabase. Поддерживается один счёт в KZT без переводов; неподдерживаемые данные останавливают подготовку.

Перед импортом закройте приложение на всех устройствах. Локальные изменения имеют приоритет при синхронизации: перед следующим запуском нужно очистить старые локальные данные целевого аккаунта, включая очередь удалений. Обычное удаление записей через интерфейс для этого не подходит.

1. Найдите UUID аккаунта по email в Supabase. Сохраните его текущие `profiles`, `categories`, `transactions`, `budgets` в закрытом каталоге `.local/imports/` (он исключён из Git).
2. Снимок должен иметь формат результата Supabase CLI: `rows[0].data` с четырьмя массивами и `rows[0].fingerprint`. Fingerprint — PostgreSQL `md5(data::text)`, где `data` — `jsonb_build_object` с массивами строк, упорядоченными по `id`. Функция `snapshot_sql` в скрипте формирует это выражение. Не вычисляйте fingerprint из сериализации Python: порядок ключей отличается.
3. Подготовьте импорт:

```sh
python3 scripts/prepare-mmbackup-import.py /path/to/file.mmbackup \
  --user-id '<UUID>' \
  --email '<EMAIL>' \
  --cloud-backup .local/imports/before-import.json \
  --output .local/imports/new-import
```

Если вместе с архивом передан размеченный `data.json`, добавьте `--data /path/to/data.json`. Флаги `exclude_from_average` переносятся для операций и категорий. Генератор сверяет SHA-256 архива, валюту, часовой пояс, полный набор исходных ID, поля записей и связи категорий; дубли ID, некорректные флаги и незавершённая проверка `needs_review` блокируют подготовку. Без `--data` флаги исключения выключены. Пометки не меняют суммы и баланс.

Скрипт проверяет целостность SQLite, валюту, связи категорий, уникальность названий и совпадение суммы операций с балансом исходного счёта. Удалённые записи пропускаются. Суммы переводятся из сотых долей без округления float. Даты интерпретируются в `Asia/Almaty` с учётом исторического смещения; другой пояс задаётся `--timezone`. Неизвестные иконки заменяются на `receipt`. `summary.json` включает количество исключённых операций и категорий, а также сумму расходов с индивидуальной пометкой. SQL проверяет количество сохранённых флагов до коммита.

4. Сверьте `summary.json` с исходным приложением. Выполните пробную копию `import.sql`, заменив только последнюю команду `COMMIT;` на `ROLLBACK;`.
5. После успешной проверки выполните `npx supabase db query --linked --file .local/imports/new-import/import.sql`. Убедитесь, что CLI связан с нужным проектом.
6. Повторно прочитайте облачные записи и сравните все поля с `payload.json`, нормализуя временные зоны и числовые суммы. Очистите старую локальную копию перед открытием приложения и синхронизацией.

SQL проверяет UUID/email и fingerprint перед удалением, блокирует конкурирующие записи на время транзакции, загружает категории перед операциями и проверяет количество и баланс до коммита. Профиль сохраняется, валюта становится KZT и устанавливается отметка инициализации. Непустые бюджеты требуют отдельного плана и блокируют подготовку.

Повторный запуск применённого SQL остановится из-за изменившегося fingerprint: после сетевой ошибки сначала проверьте результат в облаке. Идентификаторы детерминированы исходным ID и UUID аккаунта. Не пересоздавайте снимок автоматически для обхода проверки: это разрешило бы уничтожить последующие изменения пользователя.

Файлы содержат финансовые данные. Каталог результатов должен оставаться приватным; существующие файлы скрипт не перезаписывает.
