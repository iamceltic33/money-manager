# SQLite и Supabase

SQLite — основное хранилище приложения. Все действия сначала записываются локально.
Supabase хранит облачную копию. Периодичность и механизм синхронизации будут определены отдельно.

## Согласованные правила

- Категории и транзакции используют один UUID, созданный на устройстве и сохранённый в облаке без изменения.
- `user_id` соответствует идентификатору пользователя Supabase Auth.
- `exclude_from_average` есть у категории и транзакции: `0/1` в SQLite, `boolean` в Supabase. Значение по умолчанию — выключено. Исключение влияет на прогноз, но не на баланс.
- `categories.sort_order` — целое число, по умолчанию `0`.
- Название категории уникально внутри сочетания `(user_id, name, type)`.
- `category_id` может быть пустым. Удаление категории обнуляет ссылку, сохраняя транзакцию.
- Сумма положительная; направление определяет `type`: `income` или `expense`. В Supabase используется `numeric(14, 2)`. На этом этапе валюта — KZT.
- `occurred_at` — дата операции, `created_at` — дата создания, `updated_at` — дата изменения. Серверный триггер обновляет `updated_at` временем сервера; синхронизация должна учитывать возвращённое значение.
- При импорте даты без времени используется часовой пояс `Asia/Almaty`.
- `sync_status`, `sync_error` и временно сохраняемый `remote_id` — локальные служебные поля.

## Подготовка облачной схемы

Миграция `20260917000000_align_local_and_cloud_schema.sql` добавляет флаги исключения
и порядок категорий, а также создаёт недостающие профили существующих пользователей.
Существующие профили не изменяются.

## Подготовка локальной схемы

Новые записи и предустановленные категории получают UUID через `expo-crypto`.
Миграция SQLite v6 заменяет старые ID, не соответствующие формату UUID, сохраняя
ссылки транзакций на категории. Если у такой записи есть корректный `remote_id`,
используется он. Уже корректные UUID не меняются. Миграция выполняется в транзакции:
ошибка откатывает замену ID и обновление версии базы.

API проверяет название категории при создании и изменении названия или типа.
Триггеры SQLite дополнительно запрещают новые совпадения `(user_id, name, type)`,
включая запись в обход API. Сравнение чувствительно к регистру, как в облачной схеме.
Существующие дубли сохраняются вместе со связями и могут быть переименованы вручную;
редактирование остальных полей доступно. До загрузки таких категорий в Supabase
дубли необходимо устранить. Для старых записей с пустым `user_id` ограничение,
как и PostgreSQL UNIQUE, не запрещает совпадения.

## Что ещё нужно до синхронизации

- Проверить и исправить существующие дубли категорий перед отправкой в облако.
- Добавить управление запуском и согласовать расписание синхронизации. При конфликтах принят приоритет локальных правок.

Двусторонний обмен реализован; порядок и ограничения описаны в [synchronization.md](synchronization.md).

## Очередь локальных удалений

Миграция SQLite v7 добавляет `local_deletions`. Перед удалением категории или
операции триггер сохраняет владельца, тип сущности, локальный и облачный ID,
время удаления и статус `pending`. Запись в очередь и само удаление атомарны:
ошибка откатывает обе части. Очередь не имеет внешнего ключа на удаляемые записи.

Обычные таблицы по-прежнему содержат только актуальные записи: удалённые операции
сразу перестают участвовать в списках, балансе и прогнозе. Удаление категории
сохраняет связанные операции, обнуляет `category_id`, обновляет `updated_at`,
ставит `pending` и очищает прежнюю ошибку синхронизации.

`getPendingLocalDeletions(userId)` возвращает только очередь указанного аккаунта,
включая записи со статусом `failed`. Повторное удаление отсутствующей записи
не добавляет новое задание. Для записей без `user_id` задание не создаётся:
владелец облачных данных неизвестен.

Удаления сохраняются независимо от прежнего `sync_status` и наличия `remote_id`:
облачная запись могла быть создана до обрыва связи и подтверждения локально.
Механизм синхронизации учитывает следующие требования:

- Отправлять удаление по `remote_id ?? entity_id` с ограничением по владельцу.
- Считать отсутствие записи на сервере успешным удалением и очищать задание только после подтверждённого результата; при ошибке сохранять его для повтора.
- Удалять старые категории до отправки новых категорий с тем же названием.
- Не восстанавливать из облака записи, ожидающие удаления локально.
- При применении входящих удалений отдельно учитывать триггеры, чтобы не создавать бесконечный обмен одинаковыми удалениями.

Отправка очереди и применение входящих изменений реализованы с миграцией v8.
Удаления, выполненные до миграции v7, восстановить из очереди невозможно.

## Обязательства и плановые платежи: этап схемы

SQLite v10 создаёт две таблицы в транзакции миграции. Старые таблицы операций/категорий не перестраиваются. Таблицы также описаны в миграции Supabase `20261005000000_obligations_and_payments.sql`. Применение миграции к рабочему Supabase в этот этап не входило.

### `obligations`

| Поле | Назначение |
| --- | --- |
| `id`, `user_id` | ID обязательства и аккаунта; после создания не изменяются |
| `name` | Непустое название |
| `category_id` | Необязательная расходная категория того же аккаунта |
| `payment_mode` | `fixed` — одинаковая сумма; `manual` — суммы вводятся отдельно |
| `monthly_amount` | Положительная сумма для `fixed`, NULL для `manual` |
| `payment_day` | День месяца 1–31 для `fixed`, NULL для `manual`; хранится отдельно, чтобы короткий месяц не менял исходный день |
| `first_payment_date`, `last_payment_date` | Первая и последняя допустимые даты платежей включительно |
| `created_at`, `updated_at` | Время создания и изменения |

### `obligation_payments`

| Поле | Назначение |
| --- | --- |
| `id`, `user_id` | ID платежа и аккаунта; после создания не изменяются |
| `obligation_id` | Обязательство этого же аккаунта |
| `due_date` | Плановая календарная дата внутри срока обязательства |
| `amount` | Положительная сумма этого платежа; может отличаться между месяцами |
| `transaction_id` | Необязательный фактический расход своего аккаунта; NULL означает неоплаченный план |
| `created_at`, `updated_at` | Время создания и изменения |

Суммы в облаке — `numeric(14, 2)`, локально — `real` с положительной верхней границей, соответствующей облачному типу. Нормализация сумм в будущем API должна использовать существующее правило двух знаков после запятой. Плановые даты — `date` в PostgreSQL и проверенные строки `YYYY-MM-DD` в SQLite, годы 0001–9999. Это календарные даты, а не UTC-время. Месяц платежа определяется по `due_date`.

### Ограничения и связи

- Один плановый платёж на календарный месяц для одного обязательства. Отдельные обязательства могут иметь платежи в одном месяце.
- Один фактический расход можно привязать максимум к одному плановому платежу. Доходы и чужие операции запрещены. Совпадение плановой и фактической суммы/даты не требуется.
- Удаление расхода обнуляет `transaction_id`, сохраняя расписание: платёж снова неоплачен.
- Удаление категории обнуляет `category_id`, сохраняя обязательство и расходы.
- Изменение владельца/ID или типа связанной категории/операции запрещено, если оно нарушает связь.
- Нельзя сузить срок обязательства так, чтобы существующий платёж оказался за его пределами.
- Нельзя удалить обязательство, пока у него есть платежи: беззвучного каскадного удаления расписания нет. Для будущего API отдельно определить завершение, архивирование и явное удаление платежей. Удаление аккаунта Supabase по-прежнему каскадно удаляет его данные.
- PostgreSQL RLS разрешает чтение и изменение только владельцу; `anon` не имеет доступа. Проверки связей работают также при вставке/изменении в обход API.

Для будущей синхронизации локально предусмотрены `remote_id`, `sync_status`, `sync_error`, `remote_updated_at`, `local_revision`, `remote_deleted`. Правки со статусом `pending` повышают локальную ревизию. При локальном удалении категории/операции изменение ссылки отмечается `pending`; входящие удаления с `remote_deleted = 1` не переводят синхронизированную запись в `pending` только из-за отвязки.

**Текущий статус:** локальный API и обмен подключены. SQLite v11 расширяет `local_deletions` типами `obligation` и `obligation_payment`, сохраняя старую очередь и её ревизии. Миграция Supabase `20261005010000_sync_obligations.sql` расширяет `get_sync_snapshot`, `apply_sync_change` и добавляет `remove_sync_obligation`. Обе серверные миграции обязательств пока не применялись к рабочему Supabase. Таблицы и API сами по себе не меняют баланс или прогноз; интерфейс и расчёт прогноза ещё не подключены.

CRUD и правила расписания: [obligations-api.md](obligations-api.md). Обмен и совместимость старого сервера: [synchronization.md](synchronization.md#обязательства-и-расписания).

- Все SQL-миграции применены последовательно к отдельной временной PostgreSQL-базе. `tests/obligations-postgres.sql` проверяет ограничения, RLS для двух аккаунтов, запрет доступа anon и каскадное удаление аккаунта. Проверка использует минимальную имитацию Supabase Auth из `tests/fixtures/postgres-auth.sql`, а не рабочий Supabase.

- В PostgreSQL-проверке тестовые строки откатываются через `ROLLBACK`. Фикстуру auth запускать только в новом одноразовом кластере, затем последовательно все файлы `supabase/migrations/*.sql`, затем SQL-тест с `psql -v ON_ERROR_STOP=1 -f tests/obligations-postgres.sql`.
